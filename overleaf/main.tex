\begin{abstract}
  This paper presents WhyRunner, an online judge for competitive programming designed for education. It runs submissions in an \texttt{isolate} sandbox with distinct verdicts, custom output checkers, and a concurrent worker pool, and adds real-time contests, teacher-curated lessons with a class gradebook, AI-assisted problem authoring and feedback, and code similarity detection. We describe its architecture and implementation and report a reproducible performance evaluation. In a first classroom test, 30 technical high-school students solved an exercise list; the mean System Usability Scale score was 72.1, above the benchmark of 68. Contests and the instructor's perspective have not been evaluated yet.
\end{abstract}

\section{Introduction}

Competitive programming develops algorithmic thinking and problem-solving, and online judges (platforms that automatically evaluate submitted code against predefined test cases) have become common in academic settings. Most of them, however, were designed for contests and prioritize fairness and efficiency over pedagogy: students receive little more than ``Wrong Answer'' or ``Time Limit Exceeded'', with no explanation that helps them learn, and instructors find them rigid to configure for classroom use.

This work presents \textbf{WhyRunner}, an online judge designed for education with three objectives: (1) rich, automated feedback using artificial intelligence; (2) safe, scalable, multi-language execution through kernel-level sandboxing; and (3) flexible real-time contests and teacher-curated coursework. This paper describes its design and implementation (\S\ref{sec:design}), evaluates its performance with reproducible benchmarks (\S\ref{sec:performance}), and reports a first classroom evaluation in which 30 students solved one exercise list (\S\ref{sec:evaluation-status}); contests and the instructor's perspective have not been evaluated yet.

\section{Methodology}\label{sec:methodology}

Development was iterative and incremental. Requirements came from a literature review, informal conversations with students and instructors, and the author's experience with contest platforms; the main gaps found were limited pedagogical feedback, limited language support, and contest management. Several technologies were tried and discarded along the way: the submission queue moved from BullMQ (Redis), whose idle polling was costly, to AWS SQS, and finally to PostgreSQL's native \texttt{LISTEN/NOTIFY}, removing the external queue; Supabase and a separate NestJS API gave way to a standalone PostgreSQL with Drizzle ORM and Next.js Server Actions; and execution moved from per-submission Docker containers to the \texttt{isolate} sandbox (\S\ref{sec:execution-environment}).

A minimum viable product was used informally by five colleagues, with no script or questionnaire; three of their complaints became changes (submitted code shown in each attempt, a marathon-style leaderboard, and field-level errors in the JSON problem import). A security review of the web layer found that, since every exported Server Action is a public HTTP endpoint and TypeScript types are erased at runtime, some actions copied client input directly into database writes, one lacked authentication, and submission reports exposed hidden test cases; these were fixed with explicit input schemas, server-side ownership checks, and report filtering (\S\ref{sec:test-confidentiality}). Validation is technical (tests on every push and a benchmark suite, \S\ref{sec:performance}) and educational, so far one classroom test (\S\ref{sec:evaluation-status}).

\section{Related Work}\label{sec:related}

\textbf{Ataux} \cite{silva2021ataux} lets an administrator create problem lists that a class solves via Codeforces, with roles, filtering, and team registration on a React/NestJS/PostgreSQL stack; its language range is limited and its feedback correctness-only; usability was assessed with PSSUQ across 71 students. \textbf{GOJ} \cite{lima2022gamma} stores and judges problems from past UnB Programming Marathons, on a microservices architecture over AWS (SQS, SNS, S3), .NET, and MongoDB, with Bash-script judging. \textbf{Run Codes} \cite{runcodes2024}, developed by Brazilian universities, lets teachers create problem lists and contests, supports many languages, and integrates with virtual learning environments, but its complexity and external dependencies limit customized activities. \textbf{BOCA} \cite{de2004boca} is the open-source PHP/LAMP system used in Brazilian ICPC regionals; robust for traditional contests, its interface and extensibility are more limited. Table~\ref{tab:judge-comparison} compares them with WhyRunner.

\section{System Design}\label{sec:design}

WhyRunner consists of two services sharing one PostgreSQL \cite{stonebraker1986design} database: a \textbf{Next.js} \cite{nextjs2024} web application, which handles the interface, authentication (Better-Auth), and all business logic through Server Actions, with type-safe database access via Drizzle ORM \cite{drizzleorm2024}; and a \textbf{judge worker} written in Rust \cite{matsakis2014rust}, packaged with \texttt{isolate} \cite{mares2012isolate} and every language toolchain in one Docker \cite{merkel2014docker} image. The services communicate only through the database, using \texttt{LISTEN/NOTIFY} instead of an external broker. AI features are served by a chain of language models, Gemini 3.5 Flash and Flash-Lite \cite{gemini2023} and Claude Haiku 5.5 \cite{anthropic2026haiku}, called only by the web application (\S\ref{sec:ai-chain}).

\subsection{Submission Pipeline}\label{sec:submission-pipeline}

Figure~\ref{fig:submission-flow} shows the pipeline. A Server Action accepts only the problem, contest, language, and source code from the browser; every other field (status, author, question letter) is decided on the server, which also checks contest membership, start time, and rate limits. It stores the submission as \texttt{PENDING} and issues a \texttt{NOTIFY}; the judge, listening through \texttt{sqlx}'s \texttt{PgListener}, wakes its worker pool (\S\ref{sec:concurrency}). Compiled languages are compiled once, and each test case runs in a fresh \texttt{isolate} box (\S\ref{sec:execution-environment}); the output is compared according to the problem's comparison mode (\S\ref{sec:output-comparison}). Contest and standalone submissions stop at the first failing case, while lesson exercises run every case, so the pass count measures exactly how many cases were right. The final status is persisted, an in-app notification is raised, and the front-end refreshes via TanStack Query; on failure, the student may request an AI hint.

\textbf{Verdicts.}\label{sec:verdicts} Early versions reported only passed or failed. A failing submission now receives the verdict of its first failing case: \emph{wrong answer} (normal exit, mismatching output), \emph{time limit exceeded} (CPU or wall-clock limit), \emph{memory limit exceeded}, \emph{compilation error} (compiler output always shown), \emph{runtime error} (any other non-zero exit or signal), or \emph{judge error} (a sandbox or checker failure, never penalized). Without \texttt{isolate}'s control-group mode the memory cap is an address-space limit, so exceeding it makes an allocation fail with no distinct signal; the judge infers MLE when peak resident memory reached 90\% of the cap or the error output contains an allocation-failure message (e.g., \texttt{MemoryError}, \texttt{std::bad\_alloc}), a heuristic measured in \S\ref{sec:perf-verdicts}. In standings, rejected attempts on a solved problem add 20 penalty minutes, but compilation and judge errors do not count, following the ICPC \cite{icpc2024rules}.

\textbf{Test-case confidentiality.}\label{sec:test-confidentiality} Test cases are split into public samples, marked by the author, and hidden cases. The judge stores a report of the first failing case (input, expected output, program output, error output); returned unchanged, it would let a student extract hidden cases one submission at a time. As in BOCA \cite{de2004boca}, the server filters the report by viewer: the problem author sees it in full; failures on a sample are shown in full; failures on a hidden case show only the verdict, the case number, and the cases passed, also withholding the program's own output, which could simply echo its input; compiler output is always shown. In lessons, the lesson's test-visibility mode decides which cases count as visible, and the class's teachers see every report. A contest organizer who did not write the problem is treated as a participant, since any user may create a contest. The same filter applies wherever a report leaves the server, including the contest export, and the AI hint model receives the unfiltered report but returns only its answer.

\subsection{Classes, Lessons, Contests, and Workspace}\label{sec:class-lesson-model}

Alongside contests, WhyRunner offers an asynchronous mode with three entities: a \textbf{Class}, a \textbf{Lesson} (a professor-curated assignment for one class, with an optional due date), and an \textbf{Exercise} (an existing problem attached to a lesson in a fixed order). Students join with a code, submit the whole lesson at once (with confirmation if exercises are unsolved), and the professor reviews it with free-text feedback per exercise. A per-lesson test-visibility mode shows students the sample cases (default), all cases, or none. Each exercise scores the fraction of test cases passed, and a lesson sums those fractions with equal weight. Following the recommendation that programming education start with visual environments and move gradually to text \cite{audrito2012contests}, each exercise has an answer mode: \emph{code}, \emph{blocks} (Blockly blocks converted to Portugol, with a read-only panel of the generated code as a bridge to text), or \emph{Parsons} (shuffled lines of a professor solution, which must pass the tests, to be ordered and indented). The judged program is always generated on the server, so constraints, scores, and hints work unchanged, with hints adapted to the mode. A \textbf{gradebook} shows every student against every exercise, from the same snapshot and formula as the lesson review, and exports CSV (RFC 4180 quoting, UTF-8 byte-order mark, and cells starting with \texttt{=}, \texttt{+}, \texttt{-}, or \texttt{@} neutralized against CSV injection).\label{sec:contests-bank}

Problems have short codes and can be searched, filtered by difficulty and topic tags, and imported in bulk from JSON. A \textbf{contest} has a period, an optional private mode with join approval, and a cap on AI assistance (\emph{off}, \emph{concept}, \emph{hint}, or \emph{pinpoint}) enforced on the server for every request. Its leaderboard follows programming-marathon conventions: attempt counts, solve minute, first-solver marks, and ties broken by penalty. In the \textbf{solving workspace} (Figure~\ref{fig:workspace}) the editor autosaves per problem and language, every attempt keeps its submitted code, visible failures show input, own output, and expected output, and an ``Explain'' button requests a hint within the contest's cap. A home page, a command palette (\texttt{Ctrl+K}), and a notification inbox complete the interface.

\subsection{Code Similarity Detection}\label{sec:similarity}

The owner of a contest or class can request a similarity report for one problem or exercise, following MOSS's fingerprinting approach \cite{schleimer2003winnowing}. Each submission is tokenized with per-language rules; identifiers become \texttt{V}, numbers \texttt{N}, and literals \texttt{S}, while keywords and operators are kept, so renaming, reformatting, and comment edits change nothing compared. Every run of $k=5$ tokens is hashed and winnowing with window $w=4$ keeps the fingerprints, guaranteeing that any shared run of at least $w+k-1$ tokens is detected. Fingerprints present in more than half of a language's submissions (with at least four) are treated as boilerplate. For each pair of students in the same language, shared fingerprints seed matches extended while tokens agree and accepted longest first without overlap (greedy string tiling); similarity is the fraction of both programs' tokens covered. The report covers up to 300 submissions (latest or best per student) and shows matched regions side by side; the interface states that a high score is a reason to read both programs, not proof of copying.

\subsection{Execution Environment}\label{sec:execution-environment}

Earlier versions ran each submission in a sibling Docker container through the host's Docker socket mounted into the worker, which is effectively root access to the host, rules out most managed platforms, and approximated peak memory by polling \texttt{docker stats}. Execution therefore moved to \texttt{isolate} \cite{mares2012isolate}, the sandbox of the International Olympiad in Informatics, which confines one process with Linux namespaces and resource limits; all toolchains (Python, GCC/G++, \texttt{rustc}, JDK 21, Portugol) live in the judge's image. C, C++, Rust, and Java are compiled once in a box of their own (30\,s budget); then each test case runs in a fresh box (\texttt{--init}, run, read metadata, \texttt{--cleanup}) with no network; a CPU-time limit derived from the problem's limit (1\,s by default), unchanged for C, C++, and Rust, doubled plus 0.5\,s for Java, tripled for Python, and doubled plus 3\,s for Portugol; a wall-clock limit of twice the CPU limit plus 1\,s; 128\,MB of address space for C, C++, and Python, 768\,MB for Rust, and 2\,GB for the JVM languages (heap bounded by \texttt{-Xmx64m}); and at most 64 processes, which contains fork bombs. Exit code, times, peak memory, and termination cause are read from \texttt{isolate}'s metadata. \texttt{isolate} still needs \texttt{CAP\_SYS\_ADMIN} and \texttt{CAP\_NET\_ADMIN}, a much narrower grant than the Docker socket.

\textbf{Concurrent worker pool.}\label{sec:concurrency} The judge runs $N$ workers in one process (\texttt{JUDGE\_CONCURRENCY}, by default the CPU count capped at 4). A dispatcher owns the \texttt{LISTEN} connection and, on each notification or a 60\,s sweep, dead-letters submissions whose worker crashed too often and wakes idle workers. Each worker claims a row atomically with \texttt{UPDATE \ldots{} WHERE id = (SELECT \ldots{} FOR UPDATE SKIP LOCKED)}, so no two workers or replicas grade the same submission, and uses its slot number as its box id.

\subsection{Output Comparison, AI, and Solution Constraints}\label{sec:output-comparison}

Each problem chooses a comparison mode: \emph{exact} (after trimming; all older problems), \emph{tokens} (default for new problems; whitespace-insensitive), \emph{float} (tokens with numeric tolerance $\varepsilon$, $10^{-6}$ by default), or \emph{checker}, an author program for problems with several correct answers. Checkers are stored in a separate table, sent only to the owner, and run in their own box with testlib-style \texttt{input.txt}, \texttt{output.txt}, and \texttt{answer.txt}: exit 0 accepts, exit 1 is a wrong answer with the checker's message, and anything else is a judge error.

\label{sec:ai-chain}Every AI call goes through one server-side module that tries Gemini 3.5 Flash, then Flash-Lite, then Claude Haiku 5.5, with a 30\,s timeout per attempt; only transient failures (timeout, rate limiting, server errors, output failing schema validation) fall through. Prompts enclose user content in XML delimiters against prompt injection, results are localized, and calls are rate-limited per user and feature within a ten-minute window. The chain backs five features. Students may request a \emph{hint} on a failed submission, instructed to explain the logical error without giving the fix, and capped and revealed level by level in contests. Problem authors get four drafts that must be explicitly saved: a reference solution, a review of the statement with suggested edge cases, a narrative, and topic tags.\label{sec:prepublish-validation}

Before publishing, a problem's reference solution must pass its test cases through the same sandboxed execution; the pass is tied to the exact test-case and constraint content, so any edit marks it stale. Exercises may also carry \emph{solution constraints}: structural rules from a fixed catalog (maximum loop nesting, forbidden or required constructs), checked by scanning source text rather than parsing; and an optional \emph{algorithm requirement} in free text (e.g., ``must use Dijkstra's algorithm''), checked by the model chain from the requirement, language, and source, returning \texttt{\{satisfied, rationale\}}. A violation yields a distinct \texttt{CONSTRAINT\_VIOLATION} status that denies credit even though every test passed, showing the violated rule to the student.

\subsection{Integration and Deployment}\label{sec:integration}

Every push runs three GitHub Actions jobs: \emph{web} (type check, lint, 112 unit tests), \emph{judge} (formatting, Clippy, 31 tests; the 20 end-to-end sandbox tests run locally in the judge image), and \emph{enum-sync}, which fails the build when the status and language enums, declared both in Rust and in Drizzle, diverge. The judge is deployed as a persistent service with the two required capabilities, keeping its \texttt{LISTEN} connection open.

\section{Performance Evaluation}\label{sec:performance}

Every number below comes from scripts and raw results in the repository's \texttt{bench/} directory. Measurements ran on 28 October 2026 on an AMD Ryzen 5 5600 (6 cores, 12 threads) with 32\,GB of RAM, using the production judge image (\texttt{isolate} 2.7, GCC 12.2, \texttt{rustc} 1.63, OpenJDK 21, Python 3.11, Portugol 2.7.5) against a throwaway PostgreSQL 16 container; the production database was only read. This machine has far more cores than the production judge, which runs on one shared vCPU.

\textbf{Throughput and latency.} A burst of 40 or 100 submissions rotating over the six languages (five test cases each) is inserted at once, followed by one \texttt{NOTIFY}, as when a class submits together, and graded by the real judge with $N \in \{1, 2, 4, 8\}$ workers (Table~\ref{tab:concurrency}). Four workers graded 100 submissions $2.8\times$ faster than one (51\,s instead of 143\,s) and eight $3.8\times$ faster, cutting the median wait from 66\,s to 18\,s; scaling is sub-linear because compilers and JVMs compete for CPU, memory, and disk. Pinned to one CPU, four workers gave no speedup, and no spurious time-limit verdict occurred. With an idle judge, insertion to claim took about 1\,ms, so \texttt{LISTEN/NOTIFY} adds no meaningful delay; the median time to a verdict for five cases was 0.08\,s in C, 0.09\,s in Python, 0.35\,s in C++, 0.38\,s in Rust, 1.09\,s in Java, and 7.17\,s in Portugol.

\textbf{Verdict accuracy.}\label{sec:perf-verdicts} Two programs per intended verdict and language, 72 in total, were graded by the judge's real grading function; 63 (87.5\%) got the intended verdict (Figure~\ref{fig:verdicts}), and accepted, wrong answer, and time limit were always right. The Portugol runner prints compilation and runtime errors to standard output and exits with status 0, so all six such programs were graded WA; Python's two syntax errors were graded as runtime errors, since it has no compile step; and a C program writing through a failed \texttt{malloc} crashed before its memory grew, so the MLE heuristic graded it RE. Excluding Portugol, 57 of 60 verdicts were correct.

\textbf{Output comparison modes.} The 16 historical output-mismatch failures were genuine wrong answers under every mode. Rewriting the sample problems' expected outputs the way correct programs commonly differ, the exact mode rejected 3 of 35 outputs with trailing spaces and 3 of 35 with Windows line endings, tokens accepted all, and float accepted 7 of 12 different-precision numbers at $\varepsilon=10^{-6}$ and 10 of 12 at $10^{-3}$. No mode accepted a real error.

\textbf{Code similarity.}\label{sec:perf-similarity} Thirty-six hand-written solutions (four problems, Python, C, and Java, three ``authors'' each) received six automatic obfuscations each (renaming, reformatting, comment changes, function reordering, dead code, and all combined), giving 216 copy pairs, 36 hard negatives, and 162 easy negatives. Renaming, reformatting, and comments always scored 100\% (Figure~\ref{fig:similarity}); the combined obfuscation had a median of 84\% and a minimum of 37\%, while independent solutions to the same problem reached at most 68\%. The ROC AUC was 0.998, and the best-F1 threshold (0.52) gave 98.2\% precision and 99.5\% recall. Over a whole ``class'' of 21 submissions, the boilerplate filter pushed independent solutions to at most 16\%, separating copies perfectly. These systematic obfuscations make the figures an upper bound. The report took about 15\,ms for 30 students and under 0.9\,s for 300.

\textbf{Constraint checker, AI, and web.} On 30 labelled samples, the structural checker classified real violations, clean code, and identifier look-alikes correctly, but was wrong in 10 of 11 cases where the word appeared only in a string or comment. Sixty calls of the AI features through the production chain met a quota error on the primary model: 37 needed a fallback and none failed, with median latencies of 13.1--20.4\,s; generated reference solutions passed 10 of 10 in Python and 8 of 10 in C, the two failures being a sentence the last fallback model wrote before the code, which pre-publish validation catches. Standings for 1000 participants and 52\,252 submissions took 116\,ms, and a 1000-student gradebook with CSV export 267\,ms.

\section{Classroom Evaluation}\label{sec:evaluation-status}

The evaluation instrument is built into the system: when a contest or lesson ends, participants are invited to a questionnaire (eligibility checked on the server), with an informed-consent term, the System Usability Scale (SUS) \cite{brooke1996sus}, activity-specific Likert items, and open questions; a researcher-only page summarizes and exports the anonymous responses.

\textbf{Participants and procedure.} The first test took place on 29 October 2026 at IFMG, in a first-year class of the Técnico em Informática course integrated with high school. Students solved one lesson with two problems in Python and answered the student questionnaire right after; 30 responses were submitted within ten minutes. Twenty-four had never used an online judge and six had used one a few times. No contest was held and no instructor answered.

\textbf{Usability.} The mean SUS score was 72.1 (median 76.2, SD 18.3, range 22.5--95; 95\% CI about 65.6--78.6), above the benchmark of 68 \cite{sauro2011sus} and in the ``good'' range of the adjective scale \cite{bangor2009sus}. The spread is wide (Figure~\ref{fig:sus-bands}): 13 respondents scored 80.3 or more, 4 between 68 and 80, 8 between 51 and 67, and 5 below 51. Integration and learnability were the strongest items (Table~\ref{tab:sus-items}); the weakest concerned autonomy, need for support (9 of 30 agreed) and confidence, consistent with a class in which 80\% had never used a judge.

\textbf{Open answers.} What helped most was the AI assistance (about 14 mentions, e.g., ``as dicas sem entregar a resposta da IA'') and the immediate correction (about 9); all seven general comments were positive, one noting that the system ``não mostra resposta, o que é muito bom, pois desenvolve o raciocínio lógico''. The most frequent complaint (about 9) was exact output matching: both problems used the \emph{exact} mode, and in one, 26 failed submissions from 13 students differed only in whitespace and would have passed under \emph{tokens} (12 of those students passed later). Many other failures came from printing the prompt of Python's \texttt{input()}. The second complaint (about 6) was that students could not see their own output or the traceback; smaller themes included a small editor, a non-scrollable AI panel, and the wish to run code before submitting. One student reported being deaf and finding the activity somewhat hard.

\textbf{Threats to validity.} The evaluation is small and descriptive: one class, one list, one language, and a questionnaire right after a single session, with no comparison group or pre/post measure, so it shows perception, not learning gains. Thirty respondents give a reasonably stable SUS mean (about $\pm$7 points) but no subgroup analysis; novelty and social desirability (the developer was present) may have raised scores; and only students answered.

\section{Discussion}\label{sec:limitations}

The results support the design: isolated execution adds only about 5\,ms per run, the pool scales with cores, the similarity detector separates copies from independent solutions, and novice students rated usability above the benchmark. They also expose limitations. (1) \emph{AI dependency}: the fallback chain tolerates one provider's outage but not all, answers vary between models, total cost grows with users, and the last fallback model twice broke the code-only contract. (2) \emph{Sandbox}: \texttt{isolate}'s capabilities exclude many managed platforms; memory is capped per process rather than per box; and without control-group mode MLE is a heuristic that missed a crash after a failed allocation. (3) \emph{No production concurrency gain}: the production judge runs on one shared vCPU, where the pool resolves to one worker. (4) \emph{Portugol}: its errors are graded as wrong answers, and it is the slowest language, about 1.3\,s per test case. (5) \emph{Similarity scope}: comparison is same-language only and does not detect AI-generated code. (6) \emph{Heuristic constraints and visibility}: structural checks scan text and fail on strings and comments, and a lesson's ``show all'' mode reveals hidden cases of problems written by other authors. (7) \emph{Evaluation}: one class, the students' view only, and exact matching on older problems, the most frequent complaint; contests, authoring, the gradebook, and the instructor's experience remain unevaluated, so the research question is only partially answered.\label{sec:future-work}

Future work follows from these: repeat the evaluation with a contest, more classes and languages, and the instructor questionnaire, ideally with a comparison group; move older problems to \emph{tokens}; review accessibility; enable \texttt{isolate}'s control-group mode for per-box memory and a clean out-of-memory signal; deploy a multi-core judge or several replicas, which the row-level claim already supports; recognize Portugol's error messages; add signals for AI-generated code; restrict ``show all'' to the lesson owner's problems; and add languages and automated test generation.

\section{Conclusion}

WhyRunner combines a sandboxed multi-language judge with distinct verdicts, configurable output comparison, and a concurrent worker pool; real-time contests; professor-curated lessons with visual answer modes and a gradebook; AI-assisted hints and authoring behind a multi-provider model chain; pre-publish validation and solution constraints; and code similarity detection. A reproducible benchmark suite measured these components and exposed their limits. In a first classroom test, 30 students who solved one exercise list gave a mean SUS score of 72.1, above the usual benchmark, valued most the AI hints that do not give the answer and the immediate feedback, and reported problems that were fixed within two days. The evaluation is still narrow, so contests and the instructor's view are the next step.
