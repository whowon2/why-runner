## Goals / Non-Goals

**Goals:** real numbers from committed files; a long, light v4 deck the author can cut; thesis in sync; audit file corrected.

**Non-Goals:** application behavior changes; Lighthouse is optional; no classroom results (none exist).

## Decisions

- **Layout**: top-level `bench/` (`bench/judge/`, `bench/web/`, `bench/ai/`, `bench/ci/`, `bench/results/`, `bench/charts.py`, `bench/README.md`). Charts → `docs/presentation/charts/` (PNG, deck dark style; thesis uses the same PNGs).
- **DB safety**: a throwaway `postgres:16` container `whyrunner-bench-db` on port 5444, migrated with `web/drizzle/migrations`, seeded by the bench scripts. Never the shared `:5433` DB for inserts. Neon only through `PGOPTIONS='-c default_transaction_read_only=on'`.
- **Judge benches run the real code**: concurrency, e2e and verdict accuracy run the judge image against the bench DB (JUDGE_CONCURRENCY=N) and read statuses/timestamps back; per-language cost, sandbox overhead, constraint FP and compare re-grade are `#[ignore]` bench tests in `judge/` (like the existing `throughput_bench`) calling `runner`/`constraints`/`compare` directly, run in `judge:concurrency-rust` with SYS_ADMIN+NET_ADMIN. Rejected: a Python re-implementation of runner commands (drifts from the code).
- **Compare re-grade data is tiny** (≈20 historical failures across both DBs): report N honestly, and add a synthetic complement (expected outputs perturbed with trailing spaces, extra newlines, float precision) to show what each mode accepts.
- **Plagiarism**: bun script importing `web/lib/similarity`; synthetic corpus generated by deterministic transforms (rename, reformat, reorder, dead code, comments, combined) over hand-written originals plus independent solutions to the same problems, in C/C++/Java/Python.
- **AI**: bun script over `lib/ai.ts`, ≤ 20 calls per measure, records model that answered; reference solutions graded by the judge in the bench DB.
- **Web**: time `lib/gradebook.ts` and the standings computation on synthetic large classes/contests; submit latency measured as insert+NOTIFY round-trip on the bench DB.
- **Deck**: `build_v4.py` reuses v3's `Shapes` OOXML idiom, starts from v3, builds mostly new slides; lint pass counts body words (≤12) and checks notes. PDF via LibreOffice in a Debian container. Screenshots from the dev server on `DEV_PORT=3001` with the test accounts.
- **Thesis**: compiled with `latexmk` in `texlive/texlive:latest-medium`.

## Risks / Trade-offs

- [Bench numbers depend on a 12-thread desktop] → hardware in README; 1-CPU run (`--cpus=1`) reproduces the production caveat.
- [MLE heuristic misclassifies] → report measured confusion matrix as-is, list as limitation.
- [Shared dev DB used for screenshots] → only seeded demo rows via the app UI; no bench inserts there.
- [AI cost/flakiness] → small N, counted, results committed once.
